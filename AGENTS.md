# Project workflow

Run `task init` after creating a fresh worktree.

If pre-commit reports formatting or lint errors, run `task fix`; otherwise fix the underlying error.

# Ownership

OpenCode owns agent state, the app owns the window. The app renders agent capabilities and relays user decisions, but reimplements none of them.

Where OpenCode does not expose something directly, the app infers it from agent state instead of duplicating the capability (e.g. cumulative token counts summed from per-turn usage).

# Coding conventions

1. Follow newspaper style: the most important things in a file should land at its top. This can typically be achieved by placing the top-level callers at the top, and utilities they use below them.
2. Be intentional about impurity in your code - as much as possible should be pure, with side effects happening only at the edges.
3. Fail fast and loud. If somethings goes wrong unexpectedly, things should crash and burn rather than silently continuing.
4. Use the type system to your advantage. Use features such as discriminated unions, exhaustiveness checks, and return type inference. Avoid heavy use of optionals, it's code smell for "you probably should split this type into multiple cases".
5. Stay at the cutting edge, using new language features and shiny new packages, but don't use pre-release features.
6. Do not preserve backwards compatibility unless explicitly asked. Update dependents and remove obsolete paths so the codebase stays lean.

# UI conventions

1. UI copy should not use em dashes - if you want to write an em dash, use a hyphen instead.
2. When the UI names something the coding agent owns, use the agent's terminology (e.g. the panel says TODOS because OpenCode's tool deals in todos).
3. Text of arbitrary length must never break the layout - rows truncate to single-line ellipsis with the full text in a custom-styled hover tooltip, message bodies wrap instead.

# Commit messages

Format: `type(scope): message`. Keep messages short — no extended descriptions.

The scope is the affected project folder (the one containing the relevant Taskfile), comma-separated if multiple, i.e. `path/to/folder, path/to/other/folder`. Omit it when changes are repo-wide, i.e. write `type: message` in such cases.

| Type       | Use for                                  |
| ---------- | ---------------------------------------- |
| `build`    | Build tooling, including Taskfiles       |
| `chore`    | Miscellaneous housekeeping               |
| `ci`       | CI configuration                         |
| `docs`     | Documentation and comments               |
| `feat`     | New or improved end-user behavior        |
| `fix`      | Bug fixes and the tests that catch them  |
| `refactor` | Internal changes with no behavior change |
| `test`     | Test-only changes                        |

If in doubt, what changed is more important than how it changed: fixing broken tests is still `test`, build improvements are still `build`, and so on.

## Rewriting commits

It's okay to amend the last commit if it was made by you and the amendment increases clarity.

# Documentation & comment style

This applies both to dedicated documentation files and to comments in code.

1. Be brief.
2. Prefer rewriting old documentation over adding to it.
3. Do not document details that are prone to change, except when colocated with these details. We do not want documentation to go stale easily, so - when e.g. writing a README - do write about the general idea of how things work, but do not mention specific variable names unless those are at the very core of things and thus unlikely to change. If possible, avoid making lists which will need to be updated continuously.
4. Do document the reason certain choices were made, but only if the choice is unintuitive or project-specific. Do not document what is obvious from the code itself.
5. Colocate documentation with the code it describes - if it talks about a variable, put it in a comment next to the variable declaration, not at the top of the file.
6. Documentation should always read as if it's been written this way from scratch. When updating documentation after a change, do not overly focus on the change itself, but rather on the new state of the codebase overall.
7. Prefer enforcing rules strictly over documenting them.

# LLM I/O guidelines

## Isolate LLM-facing types from the rest of the codebase

*Why? Because you'll be optimizing their structure and you don't want to change code when you do.*

Keep types used for LLM I/O separate from the types you use in code, and convert between them as close to the LLM call as possible.

## Optimize LLM-facing types freely

When naming and defining the structure of LLM-facing types, think only about the LLM's understanding of it - do not apply any coding conventions.

## Constrain LLM generation when possible

Instead of asking the LLM politely to generate dates in YYYY-MM-DD format, use a type which enforces it ("day", "month", "year" fields).

## Make prompts situational

*Why? Stops the LLM from getting distracted.*

Prompts should only include information that the LLM needs to know *right now*. If the need for information is conditional, add it under that condition only.

# Development tooling rules

Use Task when possible (e.g. `task dev` instead of `cargo tauri dev`).

Prefer using CLI tools over manual operation if possible, e.g. `cp` instead of manually writing to the destination file.
